## 背景上下文（客观，供你判断，不要被任一方带偏）

**竞品 InterviewForge（这份设计的灵感来源）的真实情况**：
- 值得借鉴的是工程骨架：可插拔方法论（加岗位=加文件夹）、纯函数验证门、题库锚点+LLM改写的混合出题、组件单一职责可单测。
- 但它有三处"简历向"注水点，**运行时其实是断的**：(a) 四层记忆固化 `consolidate()` 从不被调用；(b) 7 段 ContextAssembler 不是主上下文真实路径，子 Agent 实际只发 `[system,user]`；(c) PLAN 不调模型，题序开场就确定性排好。本设计**声称刻意不抄这三处**——请验证它是否真的没有偷偷把同类注水机制引进来（比如引入了某个"看起来很厉害但实际不会被调用/不影响推理"的结构）。
- 竞品题库仅 40 道八股题、非护城河。

**本产品 m5 现状（客观）**：
- 应用层 prompt 工程已相当成熟（anti-fabrication / 反 rationalization / persona forbidden_phrases / STT 误识别容错 / 口水话计数）。
- 架构是"静态一次性出题"，纯客户端驱动 + localStorage（最近 2 场），无服务端 session 状态。
- 已有竞品没有的资产：语音 ASR/TTS、highlights→简历回填跨模块闭环。

**不可破坏的硬约束**：语音链路、4 维评分（PRD 锁定 4 维）、highlights→简历回填、公司名 scrub、skip/N-A 处理、客户端驱动 + localStorage、所有 LLM 路由 maxDuration=60。

## 请按以下维度逐项审，每个发现给出【严重度：致命/高/中/低】+【依据：文件:行 或具体推理】+【修改建议】

1. **非破坏性是否真成立**：文档反复说"失败回退到今天的行为"。逐个回退路径核实是否真能等价回退，有没有改了共享代码导致老路径被动改变的风险。文档的"核心不变量"（关掉所有新机制 = 今天的行为）是否真能保证。

2. **方法论选择机制的脆弱性**：用 JD 关键词打分（照搬竞品 `_score`）选岗位方法论——对非工程岗、JD 很短/很水、中英混写、跨领域 JD 会不会乱选或选错？`type=semi` 走哪条？回退岗位是否存在？`keyword-match.ts` 实际能力是否撑得起这个用途？

3. **动态追问的延迟与体验**：单次调用"门+生成"二合一，宣称 1-3s + "思考中"过渡可接受。在语音场景这个延迟假设是否乐观？maxDuration=60 够不够？追问预算（5题→3/10→6/15→9）是否合理？每主题≤1 追问会不会让"动态"名不副实（沦为竞品那种伪动态）？追问门由 LLM 自判要不要追——会不会过度追问或几乎不追？

4. **双层评分的真实价值 vs 复杂度**：能力维度只在 debrief 聚合、且 R1/V3.1 一次算多维——准不准？会不会和现有 4 维语义重叠让用户困惑？两个雷达在 UI 上是否冗余？这层是真有用还是"为了框架感"？

5. **题库锚点的投入产出**：维护 JSON 种子库 + keyword-match 锚点，相比"纯 LLM 生成"到底带来多少质量提升？是否值得？会不会锚点反而把 LLM 往八股方向拽、削弱"简历个性化"这个本产品优势？

6. **过度设计 / YAGNI**：`lib/m5/` 七个文件、verify 门、registry——对一个语音前端 + 客户端驱动的产品，哪些是真有用，哪些是"为了像竞品的七层"而引入的仪式性结构？哪些能砍。

7. **被遗漏的风险**：并发/竞态（follow-up 与 evaluate-turn 后台并行）、token 成本、localStorage 容量（题目变多+追问）、客户端状态机复杂度上升、面试中途刷新丢状态、旧 session 兼容、i18n、可观测性缺失。

8. **借来的竞品机制是否水土不服**：竞品是 Python 服务端 + 有界状态机；本设计是 TS 客户端驱动 + 无服务端状态。把"纯函数验证门""题库锚点""方法论 registry"搬过来，有没有因架构不同而失去原本价值、或变成花架子？
