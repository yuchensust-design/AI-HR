# 独立审核 Prompt — m5 模拟面试升级设计

> 用法：把「===== PROMPT 开始 =====」到「===== PROMPT 结束 =====」之间整段交给另一个 agent（务必给它代码库读权限）。这是一次**独立、全面**的审核——不是给前一轮做补丁检查，而是从零把整份设计重新评一遍。

===== PROMPT 开始 =====

你是一名资深 AI 工程 + 产品架构审核者。请对一份 m5 模拟面试升级设计做一次**完全独立、客观、全面**的审核。

**审核立场（重要）**：
- 你**不被任何前序意见约束**。这份设计之前有过一轮审核并据此修订，那份报告只作为**背景材料**供你参考——你**有权不同意它的任何结论**，包括重新打开它认为"已解决/已敲定"的决策、推翻它采纳的取舍。不要因为某点"前一轮通过了"就默认它对。
- 同样，也不要为了显得独立而硬挑刺。**只对代码事实和工程/产品逻辑负责**。
- **默认怀疑文档，以代码为准**；设计文档与代码冲突处，以代码为准。文档里"已纳入/已修订"是设计意图，不是已实现的代码。
- 覆盖要**全面**：架构合理性、非破坏性、可行性、过度设计/YAGNI、产品价值、遗漏风险、实施就绪度，逐一过，不要只盯局部 diff。

## 背景（客观，供判断，别被任一方带偏）
- 设计灵感来自竞品 InterviewForge（纯文字模拟面试 agent，落地"七层 harness"）。它有三处"简历向"注水点（记忆固化链 / 7段 ContextAssembler / 模型 PLAN 运行时是断的）；本设计声称"明确不做"。请独立判断它有没有以别的形式引入类似的"看着像框架、实际不被调用/不影响推理"的仪式性结构。
- 本产品 m5 现状：应用层 prompt 工程成熟，但架构是"静态一次性出题"、纯客户端驱动 + localStorage（最近 2 场）、无服务端 session 状态。已有竞品没有的资产：语音 ASR/TTS、highlights→简历回填闭环。
- 不可破坏的硬约束：语音链路、4 维评分（PRD 锁定 4 维）、highlights→简历回填、公司名 scrub、skip/N-A 处理、客户端驱动 + localStorage。

## 这份设计的核心主张（请逐一独立检验，不预设它对）
1. 用「岗位方法论（`.ts` 对象，含考察维度/出题节奏/追问树/红旗信号）」驱动出题，按 `type` + JD 关键词选方法论（bq / backend / generic-tech 兜底）。
2. 「静态主题库 + 动态追问」hybrid：每答完一题打一次 follow-up（门+生成二合一，模型钉 V3.1，客户端 8s abort，全场预算 5-10、每主题≤1），可选客户端廉价预门跳过明显答得好的题。
3. 双层评分：现有 4 表达维度不动；新增岗位能力维度，走**独立 R1 调用、与 4 维 `Promise.allSettled` 并行**，独立失败只丢自己。
4. 全部 additive、客户端驱动不变、无服务端状态；核心不变量 = 关掉所有新机制后 m5 行为与今天逐路由等价。
5. `live/page.tsx` 去重从整数 index 改 ID-based，追问 insert 到母题之后。
6. 给现有 3 个 m5 LLM 路由 + 新 follow-up 路由补 `maxDuration=60`。

## 审核维度（逐项给【严重度：致命/高/中/低】+【依据：file:line 或推理】+【建议】）
1. **架构合理性**：方案 C（客户端驱动 + 共享引擎核）对这个产品是不是对的选择？有没有更简单或更稳的做法被忽略？
2. **非破坏性 & 核心不变量**：逐条回退路径是否真成立？给出你能想到的反例（什么情况下新机制会污染老行为）。
3. **可行性（对代码核实）**：方法论选择、并行 debrief、follow-up 模型选择/超时、状态机 ID 化改造，在现有 `lib/llm.ts` 和 `live/page.tsx` 下到底能不能干、波及多大。
4. **过度设计 / YAGNI**：`lib/m5/` 各文件、verify 门、registry、双雷达、客户端预门——哪些真有用，哪些是"为了像竞品"或"为了完整"而引入的仪式？哪些能砍。
5. **产品价值**：方法论 + 动态追问 + 双层评分，对"校招学生练模拟面试"的真实价值多大？有没有投入产出倒挂的部分？会不会损害本产品"简历个性化"的既有优势？
6. **遗漏风险**：并发竞态（evaluate-turn 与 follow-up 并发同一 answer）、token/延迟成本、localStorage 配额、中途刷新/切后台/锁屏、能力维度 scrub、可观测性、i18n/无障碍——自己补全清单。
7. **实施就绪度**：§9 建造顺序是否可独立验证、可单独回退？最可能阻塞在哪？单测覆盖够不够、非纯函数部分怎么兜底？

## 输出格式
1. **总体判定**：「可直接进入实施」/「再钉 N 个小点即可（非阻塞）」/「有根本性问题需回炉重设计」。
2. 按上面 7 个维度列发现（severity + 依据 + 建议）。
3. **最高优先 3-5 条**（按重要性），以及**建议砍掉的部分**。
4. 如果你**不同意前一轮报告的某个结论**，明确指出哪条、为什么。
5. 明确指出设计哪些地方判断正确、不必动（不为挑刺而挑刺）。
6. 是否可以进入写实现计划 / 写代码——直说。
