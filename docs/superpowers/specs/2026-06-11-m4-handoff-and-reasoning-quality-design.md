## 用户报告的三个痛点(2026-06-11)

1. **跳转千人一面**:m1 结果页点「游戏策划补经历」和「计算机科学研究员补经历」,
   到 m4 看到的是同一个旧项目列表,没有按简历+目标岗位动态调整。
2. **时间维度错位**:m1 的岗位分档(现在 / 值得探索≈半年+ / 长期≈数年)和
   m4 的时间档(3-7天 / 2-4周 / 1-2月+)对不上,不知道怎么融合。
3. **推理质量**:如何根据个人经历+目标岗位(+JD+可准备时间)推出可靠的补项目内容,
   目前感觉有偏颇。

## 根因核实(已读代码确认)

### 痛点 1 = 三个真实断点

| # | 断点 | 位置 | 现状 |
|---|---|---|---|
| R1 | **表单只在无项目时显示** | `app/m4/page.tsx:463` `(projects.length === 0 \|\| showForm)` | 用户已有项目卡(如测试期建的"AIGC品牌视觉")时,从 m1 带着新目标跳过来 → 直接落在旧项目列表,`m1_target_role` 预填被静默忽略。**这正是截图里两个岗位都看到同一页的原因** —— 不是没传数据,是传了没人看。 |
| R2 | **传递上下文太薄** | `app/m1/result/page.tsx:148-163` handleGoToM4 | 只传 `{role_type, industry, employability_level, saved_at}`。m1 推荐卡上最值钱的信息全丢了:`why_fit`(内含种子缺口,如"需补游戏设计文档和玩法原型")、`match_percentage`、RIASEC code、evidence summary。 |
| R3 | **简历不共享** | `app/m1/evidence/upload/page.tsx` | m1 上传的简历只进 `m1_evidence`(summary+tags+rawSnippet),不写共享 `parsed_resume`。用户在 m1 刚传过简历,到 m4 还要再传一遍 → 嫌麻烦就跳过 → m4 没有简历可分析 → 输出趋同。 |

### 痛点 2 = 「长期」根本不该进补经历漏斗(尺度不可通约)

最初想做「缺口规模 × 时间预算」矩阵融合,**被用户否掉,理由更本质**:

- **m4 补经历 = 找工作场景工具**,时间天花板 2 个月,隐含承诺「做完简历就够投」。
- **m1「长期」= 这辈子最适合的事**:可能转行、考证、读研、数年深耕、推翻现有技能。

这不是同一把尺子的两端,是两个宇宙。给「长期」岗位生成任何 2 个月项目,
无论加多少诚实话术,本质都在暗示「这 2 个月能朝数年目标实质前进」——是假的。
`path_position`「绝不承诺可投」只是给谎言加免责声明,没解决问题。

**结论:长期退出补经历漏斗,不硬编项目。** 三个桶各归各位后矩阵自动塌掉:
- 现在可投 → 本就无 m4 链接(代码已确认),保持。
- 值得探索 → 补经历靶心,缺口真实且 ≤2 月可桥接,3 档时间在此真有意义;**此桶无尺度冲突**。
- 长期 → 摘掉「补什么经历」链接(那句话本身是假承诺),换内联诚实提示。

痛点2 是被「长期」带进来的,摘掉长期,冲突自动消失。

### 痛点 3 = 三个质量缺口

- **冷启动趋同**:无 JD 时 `analyze-gaps` 走 mode:"role" 纯靠 LLM 通识推断岗位要求,
  且收不到 m1 的个性化信号 → 不同人/不同岗位的输出趋同。
- **fixable_in 偏乐观**:LLM 倾向认为缺口在各档都"可补",没有缺口规模校准。
- **无真实市场锚**:值得探索/长期的岗位没有 JD,而 m6 手里有真岗位数据
  (`/api/m6/search-jobs`,frp 隧道,断则 mock)——完全没被 m4 利用。

## 设计

### 1. Handoff 接通(修 R1/R2/R3)

**载荷扩充**(`m1_target_role`,localStorage + DB 双写不变):

```ts
type M1TargetRole = {
  role_type: string;
  industry: string;
  employability_level: "now" | "needs_project" | "long_term";
  saved_at: string;
  // ── 新增 ──
  why_fit: string;          // 整段带过去,内含种子缺口("需补游戏设计文档和玩法原型")
  match_percentage?: number;
  riasec_code?: string;     // 如 "AIE"
  evidence_summary?: string;// m1_evidence.summary(若有)
};
```

**m4 到达逻辑**(改 `app/m4/page.tsx`):
- `?from=m1` 且 incoming `saved_at` 比上次消费的新 → **无论有无旧项目,自动展开 IntakeForm**,
  预填目标岗位;顶部 handoff 横幅:
  「📥 从测评带来:游戏策划/游戏设计师 · 值得去探索 · 测评提示需补:游戏设计文档和玩法原型」
- 旧项目列表保留在表单下方,不丢。
- 消费标记(localStorage 记录已消费的 saved_at),防刷新重复弹。

**简历直通**(修 R3,竞赛期轻量方案):
- m1_evidence.source === "resume" 时,把 rawSnippet/summary 预填进 m4 简历输入框,
  标注"来自测评时上传的简历,请确认是否最新"。
- 彻底方案(m1 上传也产出完整 parsed_resume 进共享总线)留作后续——m1 的 parse 是压缩版,
  改动面大。

### 2. 分人群而非融合:长期退出漏斗,值得探索内时间档真有意义

**不做矩阵融合**(见痛点2根因)。按 `employability_level` 分流:

#### 长期(long_term)→ 不进 m4,内联诚实提示
- m1 结果卡去掉「→ 我需要补什么经历才能做这个?」链接(对长期是假承诺)。
- 改为内联可展开的「长期方向提示」,几句话,**帮他决定要不要赌上几年,不是教他补简历**:
  1. 为什么匹配(复用现成 `why_fit`)
  2. 诚实代价:大概 1-2 年深造/考证/转行,不是这次找工作能补的
  3. 一个低成本验证第一步(找从业者聊 / 读本入门书 / 小尝试),确认值得再投入
- 实现极廉价:m1 recommend 输出对 long_term 岗位多产一个 `long_term_note` 字段,内联渲染。
  **不需要新页面、新 API、不进 m4。**

```ts
// PositiveItem 新增(仅 long_term 填充)
long_term_note?: {
  why_match: string;       // 为什么这方向适合你(可省,已有 why_fit)
  realistic_cost: string;  // 诚实代价:1-2 年深造/考证/转行
  first_validation: string;// 低成本验证第一步(非简历项目)
};
```

#### 现在可投(now)→ 保持现状(无 m4 链接)
该做的是改简历/练面试,不是补经历。维持代码现状。

#### 值得探索(needs_project)→ m4 靶心,时间档在此真有意义
只有这个桶进 m4。无尺度冲突,3 档时间正常发挥:

| 🏃 冲刺 3-7天 | 🚶 标准 2-4周 | 🧗 深耕 1-2月+ |
|---|---|---|
| 学习卡 + 明示"这是第一步,投递前还需一段标准档以上的项目" | **经典桥接项目:目标 = 从'值得探索'推进到'可投递'** | 深耕项目,含迭代/真实用户证据 |

**`path_position` 字段**(仅 m4 项目/学习卡,即只服务"值得探索"):

```ts
type PathPosition = {
  after_completion: string;   // 做完后你处在哪("可以开始投递初级游戏策划")
  honest_line: string;        // 一句诚实预期管理
};
```
(原 `remaining_steps` 删除——它是为长期设计的,长期已退出漏斗,不再需要。)

**建议档位**(gap 报告页新增):基于 `fixable_in × impact` 推荐最小有效档——
"以你的缺口,3-7 天拿不出可信证据,建议至少标准档"。用户仍可自由选,但有锚。

### 3. 推理质量增强

1. **种子缺口注入**:analyze-gaps prompt 增加「来自测评的初步判断」段
   (why_fit 的需补提示 + RIASEC 高维 + employability_level),
   要求 LLM **验证/细化/反驳,不许照抄**——治冷启动趋同,且让不同岗位的分析真正分叉。
2. **真 JD grounding**(无 JD 时的大招):mode:"role" 之前,服务端内部调 m6 的岗位搜索
   拉 1-3 条该岗位**真实在招 JD**,拼成"市场要求样本"进 prompt;
   隧道断了回退现状 generic 模式。把"LLM 拍脑袋的岗位要求"升级成"真实市场要求"。
   ——这同时是演示亮点:测评推荐的岗位,用市场上真实在招的 JD 分析差距,m1→m6→m4 飞轮闭环。
3. **fixable_in 校准规则**:prompt 写明缺口规模约束
   (如 long_term 岗位的核心硬缺口在 sprint 档默认不可补,除非给出可信理由)。
4. **(P2)怀疑者复核 pass**:第二个轻量 LLM 调用核验每条 gap 的 evidence
   是否真引用了简历原文,防幻觉;代价 +1 次调用延迟,竞赛期可缓。

## 落地方案三选一

| 方案 | 内容 | 工作量 | 治到的痛点 |
|---|---|---|---|
| **A 最小修复** | 长期退漏斗(去链接 + `long_term_note` 内联提示) + Handoff 三断点(R1/R2/R3) | ~半天-1天 | 痛点1+2 全部;痛点3 部分 |
| **B = A + 质量增强** | + 建议档位、now 不变/值得探索 path_position、种子缺口注入、fixable_in 校准 | ~1-2天 | 痛点1/2 全部;痛点3 大部分 |
| **C = B + 真 JD grounding** | + m6 真岗位 JD 进分析(隧道断回退) (+可选怀疑者复核) | ~2-3天 | 三个痛点全部;附带演示亮点 |

注:痛点2 由「长期退漏斗」直接根治(不再做矩阵融合),A 档即可拿下,无需 B/C。

## 最终定稿范围(2026-06-11 与用户确认)

实现以下 4 项;**种子缺口注入 / fixable_in 微调缓做**(理由见下):

1. **长期退漏斗**:m1 recommend 对 long_term 岗位产 `long_term_note`;m1 结果卡去 m4 链接、内联诚实提示。
2. **接通 m1→m4 三断点**(R1/R2/R3):表单被旧项目挡住 / 载荷太薄 / 简历不共享。
3. **建议档位**:gap 报告页基于 `fixable_in × impact` 给推荐档(用户仍可自由选)。
4. **C 真 JD grounding**:analyze-gaps 无 JD 时调 m6 `search-jobs` 拉 1-3 条真岗位 JD 当市场样本,隧道断回退现状 generic。

**缓做项及理由**:
- **fixable_in 校准** —— 现状已有基础规则(`analyze-gaps/route.ts:51-53`:sprint 硬技能=false、需长期积累三档=false),
  非裸奔。强化只是 prompt 加文字,可逆,等 A 跑完看是否还需要。
- **种子缺口注入** —— 「千人一面」主因是**管道断了**(数据没流到 m4),非推理弱。
  A 修好管道(真简历+真目标流通)预计解决大半;种子注入是数据流通后的推理层锦上添花,可选,
  且其传数据的一半(R2)已含在 A 中,真要补边际成本只是 prompt 多拼一可选段。

**实现顺序**:长期退漏斗 → R2(载荷)→ R1(表单展开)→ R3(简历直通)→ 建议档位 → C。

## 追加:m4 会话隔离(2026-06-11,用户反馈后)

**问题**:R1 改动暴露了 m4 一直没做会话隔离——`useM4Projects` 用「单一 master 会话」
把所有卡堆在一个全局 `m4_projects` 列表,左侧切换栏形同虚设(page 没读 `?c=`)。
从测评带新目标进来,下方仍显示别的目标的旧卡。用户要求「一个经历一个会话」。

**方案(照搬 m3 范式,DB 表 `m4_projects` 已按 conversation_id 主键)**:
- `useM4Projects(convId)`:游客单轨 localStorage(全站约定不支持多会话);
  登录 + convId → 按会话读写该行;登录无 convId → 空。
- m4 page 读 `?c=` + 编排 effect(仅登录态):`from=m1` → 开新空会话(干净表单,不串旧卡);
  有历史会话 → 跳最近一个(老用户的卡都在,不丢);无会话 → 建第一个。
- 切会话清 activeId;`from=m1` 生成后去掉 URL 的 from=m1,后续「再补一个」回归正常。
- 游客无法多会话 → 止血:handoff 表单开着时隐藏下方旧卡,避免新分析与旧卡并排。
- 老用户的卡平滑保留为「那个 master 会话」,不删不丢。

**验证**:游客 from=m1 → 横幅/种子缺口/表单展开/简历预填/旧卡止血隐藏全过,无报错;
游客无 handoff → 旧卡正常显示。登录态隔离逻辑与 m3 同构,tsc+build 通过。

## 追加:项目详情两项交互(2026-06-11,用户反馈后)

1. **Ask AI 改多轮对话**:`/api/m4/ask` 接收 `messages[]` 历史(向后兼容单 `question`),
   项目上下文进 system,聊天串渲染气泡 + 自动滚底 + 清空对话。最多保留近 12 轮。
2. **勾选任务 → AI 整理笔记草稿**:周计划勾选任务后,笔记卡出现「✦ 根据已勾选的 N 个任务整理草稿」
   按钮 → 调新 route `/api/m4/draft-notes` → 填进可编辑的笔记框。
   **反编造关键**:草稿只把任务组织成叙述,真实成果/数字一律用【】占位 + 末尾 ⚠️ 提示用户填真实值,
   绝不替用户声称成果;committable 仍需 DONE + ≥10 字。仅项目卡有(学习卡无任务,不出此按钮)。

验证:多轮 ask 跟进问题答出上下文相关;draft-notes 输出含【】占位与 ⚠️ 行、无编造数字;
详情页渲染无报错,勾选任务后按钮文案随之更新。tsc+build 通过。

「再补一个」按钮已删(会话隔离后,换目标=左侧新建会话,不再需要同会话内换上下文入口)。

3. **「送进简历优化」从项目头部移到笔记卡底部**:写完笔记就地一步送出,符合「写完→送出」的自然顺序。
   头部 StatusActions 只留「推进状态 / 删除」。笔记卡按状态给上下文提示:
   未完成→「做完后标完成+填够10字可送」;DONE 未达标→「写够10字实际成果就能送」;committable→出送出按钮。
4. **笔记保存:显式「保存到云端」按钮 + 状态**(用户对静默自动存不放心 + 担心退登/换设备):
   - 现状:登录态本就 onChange 即 upsert 到 DB(换设备能看到);游客只存 localStorage(本机)。
   - 登录态:笔记卡加「💾 保存到云端」按钮 → `useM4Projects.saveToCloud()` 显式 upsert + 反馈
     「✓ 已保存到云端 · 时间」/ 失败提示。auto-save 仍在(安全网),按钮给控制感+确认。
   - 游客:不给按钮,给提示「游客笔记只存在本机,登录后存云端,换设备/重登也能看到」+ 登录链接,
     诚实说明本地 only 的边界。

## 铁律(沿用)

- 改动的 route 必带 `export const maxDuration = 60`。
- 表单字段永不折叠;handoff 预填也要可见可改。
- 反编造纪律不放松:path_position 是诚实条款的延伸,不是营销话术。
- 改完 dev server 实点验证(m1 答题→点补经历→看预填→出卡全链路);未经同意不提交。

  long_term 岗位 deep 档 → 出 remaining_steps;隧道断 → 真 JD grounding 静默回退。
